TASK1. Инструменты автоматизации в Grafana

Введение
Grafana – стандартная промышленная среда для мониторинга высоконагруженных систем.
Есть два распространенных подхода к работе с дашбордами (dashboards) в Grafana: ручное изменение и автоматизированная генерация. Ручное редактирование уместно для простых компонентов системы, логика которых существует в некотором единственном экземпляре и является достаточно уникальной. Для параметризации дашборд активно применяют селекторы (variables): например, с их помощью можно выбирать датацентр, номер пода и т.п. Впрочем, если логика “разрослась” и число ручек и сервисов становится большим, то активно применяют автоматическую генерацию борд с помощью скриптов.
В этой домашней работе вам необходимо разработать небольшой pet-project, который включает следующие компоненты:
1. Имплементация мониторинга для экспорта метрик ручек для мониторинга latency, traffic и errors (три из четырех золотых сигналов; saturation в этой работе не рассматривается)
2. Генератор дашборда с метриками ручек для микросервиса
3. Скрипт для “обстрела” (создания небольшой нагрузки на ручки микросервиса)
Подготовительная часть
Работу можно выполнять на любых языках программирования и на любом стеке (language-agnostic), если для них существует зрелый клиент Prometheus. В частности, можно использовать Python, Java, Kotlin, Go, C#, Rust, C++, Haskell.
Перед началом работы, реализуйте простой микросервис ровно с тремя REST-ручками:
* POST /items – создать запись,
* GET /items/{id} – получить запись (для несуществующего id возвращается 404),
* PUT /items/{id} – обновить запись.
Кроме них, у сервиса должна быть служебная ручка GET /health, которая возвращает 200, когда сервис готов принимать запросы. В качестве слоя хранения используйте in-memory хранилище (хранить данные в структурах данных рантайма). Нам требуется некоторая каноническая имплементация простого CRUD-хранилища.
Необходимо завернуть приложение в Docker-контейнер и предоставить docker-compose.yaml для запуска.

Часть 1. Реализация библиотеки
Скорее всего, для вашего языка существуют некоторые канонические способы, как прикрутить к REST-ручкам Prometheus-метрики. К таким способам могут относиться:
* ручная регистрация ручки через прокси-класс
* аннотации на методах
* обертка тела метода с помощью лямбда-функции
* middleware-обработчик запросов
* и т.д.
Вам необходимо воспользоваться существующим идиоматичным средством вашего языка (технологией программирования), чтобы добавить сбор золотых сигналов с REST-ручек. Необходимо, чтобы для каждой ручки (кроме служебных /health и /metrics) собирались следующие сигналы:
1. Latency – так, чтобы по метрикам можно было построить перцентили 50, 95 и 99
2. Throughput – так, чтобы по метрикам можно было построить RPS
3. Errors – число ответов с кодами 4xx и 5xx с разбивкой по конкретному коду ответа
Перцентили должны оставаться корректными при агрегации по нескольким экземплярам приложения. Подумайте, какой тип метрик Prometheus позволяет это сделать, и обоснуйте свой выбор в README.
Необходимо, чтобы метрики учитывали (в виде лейблов):
1. Номер пода
2. Датацентр, в котором расположен под
3. Идентификатор ручки (HTTP-метод и шаблон пути, например /items/{id}, а не фактический путь запроса)
4. Код ответа (там, где это необходимо)
Названия метрик и лейблов выберите самостоятельно и кратко опишите в README.
Неизвестные на этапе компиляции приложения параметры (номер пода, датацентр) пробрасывайте с помощью environment-переменных POD_ID и DATACENTER. Убедитесь, что метрики в вашем модельном приложении отдаются в формате Prometheus по ручке GET /metrics.

Часть 2. Инструментарий для генерации дашборд
Добавьте в docker-compose.yaml развертывания для Prometheus и Grafana. Зафиксируйте версии образов (не используйте тег latest). Запустите два экземпляра вашего приложения (из одного образа, с разными значениями POD_ID и DATACENTER, имитирующими два датацентра) и настройте Prometheus так, чтобы он скрейпил оба экземпляра. Источник данных (datasource) Prometheus в Grafana должен создаваться автоматически через файл provisioning, с фиксированным uid, чтобы на него можно было сослаться из дашборда.
Доработайте вашу библиотеку так, чтобы приложение отдавало список своих ручек (по ручке GET /handlers; формат ответа выберите самостоятельно).
Разработайте CLI-скрипт, который будет генерировать дашборд в Grafana для запущенного приложения, получая в рантайме список ручек от приложения. Язык скрипта – на ваше усмотрение. Можно воспользоваться официальным REST API Grafana, в том числе вместе с каким-либо SDK для построения дашборда, либо собирать JSON дашборда самостоятельно. Если вы используете SDK, зафиксируйте его версию, совместимую с выбранной версией Grafana. Скрипт должен запускаться через docker-compose после того, как отработали health-проверки приложения и Grafana (depends_on с condition: service_healthy).
Доступ скрипта к Grafana осуществляется с учетными данными администратора, которые передаются через переменные окружения (подробнее см. требования к секретам ниже).
Результатом запуска docker compose up должно стать то, что можно открыть Grafana и увидеть дашборд с ручками вашего приложения. Для каждой ручки на дашборде должны быть панели, показывающие:
1. Latency (перцентили 50, 95 и 99)
2. RPS
3. Ошибки по кодам ответа
На дашборде должны быть селекторы датацентра и номера пода (с возможностью выбрать несколько значений или “All”). Запросы PromQL должны корректно агрегировать значения по выбранным датацентрам и подам: для rate используйте sum, а перцентили считайте по агрегированным бакетам (histogram_quantile поверх суммы по le). Дашборд должно быть нельзя редактировать (non-editable).
Список ручек не должен быть прописан в самом скрипте: если в приложении появится еще одна ручка, то после перезапуска стека она должна появиться на дашборде без изменений кода генератора.

Часть 3. Нагрузочный инструмент
Существуют различные инструменты для нагрузочного тестирования – wrk, JMeter, k6 и т.д. Для создания небольшой фоновой нагрузки вы можете воспользоваться ими или написать свой простой инструмент – все варианты принимаются.
Напишите скрипт (или настройте инструмент), который запускается внутри вашего docker-compose.yaml после того, как приложение прошло health-проверку, а генератор дашборда успешно завершил работу (condition: service_completed_successfully). Он должен постепенно (в течение нескольких минут) нарастить нагрузку до фоновой, порядка 20-50 RPS суммарно на оба экземпляра приложения, и поддерживать ее, пока стек не будет остановлен. Нагрузка должна затрагивать все ручки и оба экземпляра приложения.
Сделайте так, чтобы некоторый процент запросов (несколько процентов) завершался ошибкой, причем на дашборде должны быть видны ошибки как минимум двух разных кодов, например 404 и 500. Способ получения ошибок выберите самостоятельно (например, запросы к несуществующим id и/или искусственные сбои в сервисе с настраиваемой вероятностью).
