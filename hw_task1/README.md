# Мониторинг REST API с помощью Prometheus и Grafana

Домашняя работа №1 по дисциплине «Высоконагруженные системы».

Проект представляет собой систему мониторинга REST API на FastAPI с использованием Prometheus и Grafana. Реализован сбор трёх золотых сигналов мониторинга: latency, traffic и errors, автоматическая генерация дашборда и имитация постоянной нагрузки на приложение.

## 1. Стек технологий

- Python 3.14, FastAPI — реализация REST API.
- prometheus-client — сбор и экспорт метрик.
- Prometheus 3.5.0 — сбор и хранение метрик.
- Grafana 11.6.3 — визуализация метрик.
- HTTPX — взаимодействие с HTTP API и генерация нагрузки.
- Docker и Docker Compose — контейнеризация и запуск компонентов.

## 2. Архитектура

Система состоит из пяти основных компонентов:

1. **Items Service** — REST API с хранением данных в оперативной памяти. Запускается в двух экземплярах из одного Docker-образа.
2. **Prometheus** — собирает метрики с обоих экземпляров приложения каждые 5 секунд.
3. **Grafana** — отображает метрики на автоматически созданном дашборде.
4. **Dashboard Generator** — получает список REST-ручек через `/handlers`, формирует дашборд и публикует его через Grafana API.
5. **Load Generator** — создаёт фоновую нагрузку с постепенным увеличением интенсивности до 30 RPS.

Экземпляры приложения имитируют размещение в двух датацентрах:

- `app-1`: POD_ID=pod-1, DATACENTER=dc-1.
- `app-2`: POD_ID=pod-2, DATACENTER=dc-2.

Оба экземпляра используют независимые in-memory хранилища.

## 3. Запуск проекта

### Требования

Для запуска необходимы Docker и Docker Compose.

### Запуск

Из директории `hw_task1` выполнить:

```bash
cp .env.example .env
docker compose up
```

При необходимости можно изменить пароль администратора Grafana в файле `.env`.

Docker Compose автоматически:

1. Запускает два экземпляра приложения.
2. Проверяет их готовность через healthcheck.
3. Запускает Prometheus и Grafana.
4. Создаёт дашборд через Grafana API.
5. Запускает генератор нагрузки после успешного создания дашборда.

Через 2–3 минуты после запуска в Grafana отображаются данные под нагрузкой.

### Адреса сервисов

- Первый экземпляр FastAPI: http://localhost:8001
- Второй экземпляр FastAPI: http://localhost:8002
- Prometheus: http://localhost:9090
- Grafana: http://localhost:3000
- Дашборд: http://localhost:3000/d/items-service-monitoring

Для входа в Grafana используются учётные данные из `.env`.

### Остановка

```bash
docker compose down
```

## 4. REST API

Реализованы три основные ручки:

- `POST /items` — создание записи.
- `GET /items/{id}` — получение записи по идентификатору.
- `PUT /items/{id}` — обновление записи.

Дополнительные служебные ручки:

- `GET /health` — проверка готовности приложения.
- `GET /metrics` — экспорт метрик в формате Prometheus.
- `GET /handlers` — получение списка REST-ручек.

Данные хранятся в словаре Python. При перезапуске приложения содержимое хранилища сбрасывается.

Для несуществующего идентификатора возвращается HTTP 404.

## 5. Метрики Prometheus

Для сбора метрик используется middleware FastAPI, который измеряет длительность запросов и регистрирует коды ответов.

### 5.1. Latency

**Метрика:** `http_request_duration_seconds`

**Тип:** Histogram.

Измеряет время обработки HTTP-запросов в секундах.

Экспортируются временные ряды:

- `http_request_duration_seconds_bucket`
- `http_request_duration_seconds_count`
- `http_request_duration_seconds_sum`

#### Почему выбран Histogram?

В данной работе необходимо рассчитывать перцентили latency (p50, p95, p99) с учётом нескольких экземпляров приложения.

Histogram позволяет агрегировать значения бакетов разных экземпляров приложения, после чего рассчитывать перцентили с помощью `histogram_quantile()`.

Пример PromQL для p95:

```promql
histogram_quantile(
  0.95,
  sum by (le) (
    rate(http_request_duration_seconds_bucket[5m])
  )
)
```

Усреднение перцентилей, рассчитанных отдельно для каждого экземпляра, не даёт корректного общего перцентиля.

Перцентили Histogram являются приближёнными, а их точность зависит от выбранных границ бакетов.

### 5.2. Traffic

**Метрика:** `http_requests_total`

**Тип:** Counter.

Счётчик регистрирует количество обработанных HTTP-запросов.

Для расчёта RPS используется скорость изменения счётчика:

```promql
sum(rate(http_requests_total[5m]))
```

### 5.3. Errors

Ошибки учитываются той же метрикой `http_requests_total`.

Для получения интенсивности ошибок используются ответы с кодами 4xx и 5xx, сгруппированные по конкретному HTTP-коду:

```promql
sum by (status_code) (
  rate(
    http_requests_total{status_code=~"4..|5.."}[5m]
  )
)
```

### 5.4. Лейблы метрик

Используются следующие лейблы:

- `method` — HTTP-метод запроса.
- `handler` — шаблон маршрута, например `/items/{id}`.
- `pod_id` — идентификатор экземпляра приложения.
- `datacenter` — идентификатор датацентра.
- `status_code` — HTTP-код ответа (для Counter).
- `le` — верхняя граница бакета Histogram.

Значения `pod_id` и `datacenter` задаются через переменные окружения `POD_ID` и `DATACENTER`.

Вместо фактических URL используются шаблоны маршрутов, чтобы избежать неконтролируемого увеличения количества временных рядов.

Служебные ручки `/health`, `/metrics`, `/handlers`, а также маршруты документации FastAPI исключены из мониторинга.

Запросы к неизвестным маршрутам могут учитываться с лейблом `handler="unmatched"`.

## 6. Автоматическая генерация дашборда Grafana

Генератор реализован на Python и использует Grafana HTTP API.

Алгоритм работы:

1. Генератор обращается к `/handlers` приложения.
2. Получает список зарегистрированных REST-ручек.
3. Формирует для каждой ручки три панели: Latency, RPS и Errors.
4. Создаёт или обновляет дашборд через Grafana API.

Для каждой ручки создаются следующие панели:

- **Latency** — p50, p95 и p99.
- **RPS** — количество запросов в секунду.
- **Errors** — интенсивность ошибок с разбивкой по HTTP-кодам.

Дашборд содержит селекторы `Datacenter` и `Pod`, поддерживающие множественный выбор и `All`.

PromQL-запросы агрегируют данные по выбранным экземплярам приложения.

Для RPS и ошибок используется `sum(rate(...))`, для перцентилей — `histogram_quantile()` по агрегированным бакетам с сохранением метки `le`.

Дашборд имеет фиксированный UID `items-service-monitoring` и настроен как non-editable.

Источник данных Prometheus создаётся автоматически через Grafana provisioning с фиксированным UID `prometheus-main`.

**Список REST-ручек не прописан в генераторе вручную.** При добавлении новой ручки после перезапуска стека для неё автоматически создаются соответствующие панели.

Генератор запускается только после успешного прохождения healthcheck приложений и Grafana.

## 7. Генерация нагрузки

Нагрузочный скрипт написан на Python с использованием асинхронного клиента HTTPX.

Параметры нагрузки:

- Целевая интенсивность: 30 RPS суммарно.
- Время разгона: 120 секунд.
- Количество экземпляров приложения: 2.
- Используемые HTTP-методы: POST, GET, PUT.
- Доля искусственных ошибок: приблизительно 4%.

Генератор постепенно увеличивает количество запросов и после достижения целевой нагрузки продолжает работать до остановки стека.

Нагрузка распределяется между двумя экземплярами приложения.

### 7.1. Имитация ошибок

Для демонстрации мониторинга ошибок предусмотрены два сценария:

- **404 Not Found** — GET-запрос к несуществующему идентификатору.
- **500 Internal Server Error** — GET-запрос к `/items/-1`.

Идентификатор `-1` используется исключительно для имитации внутренней ошибки сервиса в рамках нагрузочного тестирования.

Вероятность каждого типа ошибки составляет приблизительно 2% от общего количества запросов.

### 7.2. Автоматический запуск

Нагрузочный генератор запускается после успешного завершения генератора дашборда.

Для этого используется Docker Compose с зависимостью:

```yaml
depends_on:
  dashboard-generator:
    condition: service_completed_successfully
```

После достижения целевой интенсивности нагрузка поддерживается до остановки контейнера.

## 8. Работа с секретами

Учётные данные администратора Grafana передаются через переменные окружения.

В репозитории находится файл `.env.example` с примером конфигурации.

Локальный файл `.env` исключён из Git через `.gitignore`.

Пароль администратора не записывается непосредственно в исходный код или публикуемые конфигурационные файлы.

## 9. Особенности реализации

- Датацентры моделируются с помощью двух Docker-контейнеров.
- Для обоих экземпляров приложения используется один Docker-образ.
- Каждый экземпляр имеет собственное in-memory хранилище.
- Prometheus автоматически собирает метрики обоих экземпляров.
- Grafana использует автоматически настроенный datasource.
- Дашборд создаётся программно без ручной настройки панелей.
- Генератор определяет REST-ручки динамически.
- Нагрузочный генератор поддерживает постоянную фоновую нагрузку.
- Весь стек запускается через Docker Compose.

Проект предназначен для демонстрации принципов мониторинга высоконагруженных систем в учебных целях.
