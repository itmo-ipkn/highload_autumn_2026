### 1. Мониторинг HTTP-запросов

Для сбора метрик используется middleware `Monitor.Handle`

Через неё регистрируются HTTP-обработчики, и для каждого запроса автоматически измеряются:

- время выполнения
- количество запросов 
- HTTP-код ответа

### 2. Выбор метрик

Для мониторинга я использовал два типа метрик:

- **Counter `http_requests_total`** - количество HTTP-запросов
- **Histogram `http_request_duration_seconds`** - распределение времени выполнения запросов. Для p50, p95 и p99

Для latency выбран именно Histogram, тк нужно корректно объединять данные нескольких экземпляров приложения
Summary здесь не подходит, если каждый под самостоятельно посчитает p99, усреднить эти значения и получить общий p99 нельзя
Histogram позволяет сначала сложить счётчики бакетов разных подов, а затем вычислить перцентиль по общему распределению

Для разделения метрик используются четыре лейбла: `pod`, `dc`, `handler` и `code`

В `handler` сохраняется шаблон маршрута, например `GET /items/{id}`. Это нужно, чтобы не создавать отдельную временную серию для каждого ID

### 3. Запросы PromQL

Приложение отдаёт в `/metrics` только накопленные счётчики: сколько запросов было с момента старта и сколько из них уложилось в каждый бакет времени

RPS, ошибки и перцентили из этих счётчиков вычисляет Prometheus по PromQL-запросам

Эти запросы формирует генератор дашборда, по одному набору на каждую ручку

**Фильтр по ручке, датацентрам и подам**

В каждом запросе есть одинаковый фильтр:

```promql
{handler="GET /items/{id}", dc=~"$dc", pod=~"$pod"}
```

- `handler` — для какой ручки строится график
- `$dc` и `$pod` — значения из селекторов дашборда

**RPS**

```promql
sum(rate(http_requests_total{handler="GET /items/{id}", dc=~"$dc", pod=~"$pod"}[$__rate_interval]))
```

- `http_requests_total` - общий счетчик
- `rate(...)` - насколько счётчик вырос за последний отрезок времени, и пересчет это в запросы в секунду 
- `sum(...)` - складывает их в одно число, общий RPS ручки на выбранных подах

**Ошибки кол-во**

```promql
sum by (code) (rate(http_requests_total{handler="GET /items/{id}", code=~"4..|5..", dc=~"$dc", pod=~"$pod"}[$__rate_interval]))
```

Тоже самое что и RPS, но с фильтром `code=~"4..|5.."` -> остаются только ответы с кодами 4xx и 5xx

`sum by (code)` складывает поды, но разбивку по коду сохраняет

**Latency p50, p95 и p99**

```promql
histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket{handler="GET /items/{id}", dc=~"$dc", pod=~"$pod"}[$__rate_interval])))
```

1. `http_request_duration_seconds_bucket` - бакеты гистограммы. Каждый бакет считает, сколько запросов выполнилось не дольше своей границы `le`: не дольше 5 мс и т.д.
2. `rate(...)` - сколько запросов в секунду попадает в каждый бакет
3. `sum by (le)` - бакеты разных подов складываются, а разбивка по границам `le` остаётся
4. `histogram_quantile(0.99, ...)` по общему распределению находит время, быстрее которого выполнились 99% запросов

Важен порядок: сначала складываются бакеты, и только потом считается перцентиль

Если посчитать p99 на каждом поде отдельно и усреднить, результат будет неправильным

Поэтому для latency нужен Histogram, а не Summary

### 4. Автоматическая генерация дашборда

Генератор написан на Go

Служебный endpoint `/handlers` возвращает список обработчиков, зарегистрированных через `Monitor.Handle`

При запуске генератор получает этот список от приложения, убирает дубликаты и формирует JSON для Grafana

Для каждой ручки создаётся отдельная строка с тремя панелями: Latency, RPS и Errors

Сверху дашборда — строка Overview с общей картиной по всем ручкам: RPS, доля ошибок в процентах и p99 latency, на каждом графике по линии на ручку. Ручки в этих запросах не перечисляются — `sum by (handler)` сам даёт отдельную линию для каждой

После этого генератор отправляет дашборд в Grafana через REST API

Преимущество такого решения в том, что при добавлении новой HTTP-ручки не нужно изменять код генератора.


### 5. Генерация нагрузки

k6

Сценарий постепенно увеличивает нагрузку с 5 до 40 RPS за три минуты, а затем поддерживает её

Запросы распределяются между двумя экземплярами приложения и затрагивают все три ручки

Ошибки, два случая:

- **404** - часть запросов обращается к несуществующему ID.
- **500** - приложение с небольшой вероятностью имитирует внутреннюю ошибку.

Также добавил искусственную задержку выполнения запросов, тк данные хранятся в памяти, сервис обычно отвечает слишком быстро, и разницу между p50, p95 и p99 практически не видно

### 6. Запуск всей системы

Запуск через Docker Compose: два экземпляра Go-сервиса, Prometheus, Grafana, генератор дашборда и k6

Порядок запуска настроен через healthcheck и `depends_on`

Сначала должны стать доступными приложения и Grafana

Затем запускается генератор дашборда. Только после его успешного завершения стартует нагрузка
