# Мониторинг Items API

Учебный сервис на Go и chi. Записи хранятся в памяти и пропадают при перезапуске.
Работают два экземпляра, Prometheus и Grafana. Дашборд и фоновая нагрузка запускаются автоматически.

## Запуск

Нужен Docker Compose. Устанавливать Go на компьютер не обязательно.
Выполняйте команды из папки `hw-1`.

```sh
cp .env.example .env
docker compose up
```

| Сервис | Адрес |
| --- | --- |
| API: `pod-1`, `dc-a` | http://localhost:18081 |
| API: `pod-2`, `dc-b` | http://localhost:18082 |
| Prometheus | http://localhost:19090 |
| Grafana | http://localhost:13000 |

Порты и учётные данные Grafana заданы в `.env`; файл исключён из Git.
После изменения Go-кода используйте `docker compose up --build`.
Остановка: `docker compose down`. Данные API потеряются, история метрик и настройки Grafana сохранятся.
Пароль из `.env` применяется при первом запуске Grafana; изменение файла не меняет пароль в её существующей базе.

## Ручки

| Запрос | Результат |
| --- | --- |
| `POST /items` | Создать запись, ответ 201 |
| `GET /items/{id}` | Получить запись, ответ 200 или 404 |
| `PUT /items/{id}` | Заменить запись, ответ 200 или 404 |
| `GET /health` | Проверить готовность |
| `GET /metrics` | Получить метрики Prometheus |
| `GET /handlers` | Получить методы и шаблоны бизнес-ручек |

Тело POST и PUT: `{"name":"книга","value":"первое издание"}`.
Имя обязательно, до 200 байт; `value` — строка. Неверный JSON или ID дают 400.
PUT не создаёт отсутствующую запись. Тело запроса ограничено 64 КиБ.

```sh
curl -X POST http://localhost:18081/items \
  -H 'Content-Type: application/json' \
  -d '{"name":"книга","value":"первое издание"}'

# Подставьте id из ответа POST.
curl http://localhost:18081/items/1
curl http://localhost:18081/metrics
```

## Метрики

| Имя | Тип | Лейблы |
| --- | --- | --- |
| `items_api_requests_total` | Counter | `pod_id`, `datacenter`, `method`, `route`, `status_code` |
| `items_api_request_duration_seconds` | Histogram | `pod_id`, `datacenter`, `method`, `route` |

`POD_ID` и `DATACENTER` приходят из окружения. Экземпляры используют пары `pod-1` / `dc-a` и `pod-2` / `dc-b`.
В `route` пишется шаблон `/items/{id}`, а не конкретный ID.
Служебные запросы и неизвестные пути не учитываются. Метрики появляются после первых бизнес-запросов.

Счётчик нужен для RPS и ошибок по кодам ответа. Гистограмма измеряет время обработки в секундах.
Для общего перцентиля сначала суммируем скорости изменения одинаковых бакетов по подам,
затем применяем `histogram_quantile`. Усреднять готовые p95 нельзя.
Точность ограничена шириной бакетов; границы одинаковы у всех экземпляров.

`/handlers` строится из роутера. Новую ручку регистрируем через `measured` в `internal/api/api.go`.

Prometheus опрашивает оба `/metrics` каждые 5 секунд. В Grafana источник создаётся
из файла provisioning с постоянным UID `items-prometheus`.

## Дашборд

Откройте http://localhost:13000/d/items-api-overview.
На каждую ручку есть панели p50/p95/p99, RPS и ошибок по HTTP-кодам.
Фильтры «Датацентр» и «Под» поддерживают несколько значений и All.

Генератор читает `/handlers` обоих приложений и отправляет JSON в Grafana.
Повторный запуск обновляет тот же дашборд; редактирование в нём отключено.
Используется HTTP API `/api/dashboards/db`, проверенный на закреплённой версии Grafana.
Контейнер `dashboard` завершается с кодом 0 после публикации — это нормально.

```sh
docker compose run --rm dashboard
```

## Нагрузка

Контейнер `load` ждёт готовности API и успешного завершения `dashboard`.
За 150 секунд темп растёт от 1 до 30 RPS суммарно, затем держится до остановки.
Запросы идут по очереди к обоим экземплярам: POST, GET и PUT.
ID для чтения и обновления берётся из ответа своего экземпляра.

В каждом цикле из 100 запросов на экземпляр два POST дают 400 (пустое имя),
два GET — 404 (отсутствующий ID). Остальные запросы успешны.
Медленные ответы снижают фактический RPS; неожиданные ошибки пишутся в лог.
POST постоянно добавляет записи, поэтому память постепенно растёт — это учебный стенд.

Остановить только нагрузку: `docker compose stop load`.
Запустить снова: `docker compose up -d load`.
Для другого темпа можно запустить `docker compose run --rm load -rps 20 -ramp 2m`
после остановки основного `load`.

## Проверки

```sh
docker build --target test -t highload-hw1-test:local .
```

Проверяются API, конкурентный доступ, метрики, дашборд и сценарий нагрузки. Запускаются race detector и `go vet`.
В http://localhost:19090/targets оба экземпляра должны иметь состояние UP.

## Код

- `internal/items` — хранилище и блокировки.
- `internal/api` — ручки и проверка запросов.
- `internal/monitoring` — метрики и список ручек.
- `cmd/app` — запуск и остановка сервера.
- `internal/dashboard` — запросы, панели и клиент Grafana.
- `cmd/dashboard` — запуск генератора.

- `internal/load` — темп и сценарий нагрузки.
- `cmd/load` — запуск нагрузочного клиента.
