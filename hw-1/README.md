# Каталог товаров — ДЗ №1

Два экземпляра TypeScript + Fastify и Prometheus. Каждый API работает одним процессом со своим хранилищем в памяти; после перезапуска его товары теряются. Датацентры имитируются лейблами на одном компьютере.

## Docker Compose

Из каталога `hw-1/`, при запущенном Docker Desktop / Docker Engine:

```bash
cp .env.example .env
docker compose up
```

Node.js на хосте не требуется. Первый запуск собирает образ и загружает зависимости. API-1: http://127.0.0.1:18080, API-2: http://127.0.0.1:18081, Prometheus: http://127.0.0.1:9090. Готовность API проверяется через `/health`. Порты меняются через `API_1_PORT`, `API_2_PORT`, `PROMETHEUS_PORT` в `.env`; внутренний порт каждого API — 3000. `.env` не хранится в git, секреты на этом этапе не требуются.

```bash
docker compose ps
docker compose down
# После изменения исходников:
docker compose up --build
```

## Команды Make

Команды работают из корня репозитория и из `hw-1/`. Если `.env` отсутствует, он автоматически копируется из `.env.example`; существующий файл сохраняется.

| Команда | Действие |
|---|---|
| `make up` | Запуск в фоне с ожиданием готовности |
| `make stop` | Остановка контейнеров |
| `make down` | Остановка и удаление контейнеров с сохранением томов Prometheus и Grafana |
| `make rebuild` | Пересборка API и пересоздание контейнеров с ожиданием готовности |
| `make ps` | Состояние контейнеров |
| `make logs` | Просмотр последних 100 строк и новых логов |

`make rebuild` сбрасывает товары в памяти API; история Prometheus сохраняется. В текущем Compose `make up` также проверяет сборку API через `pull_policy: build`, используя кеш Docker.

## API

Товар: `{ "id": "UUID", "name": "Клавиатура", "price": 450000 }`. Цена — целое число копеек (450000 = 4500 ₽), от 0 до 9007199254740991. Имя — 1–200 символов после trim. POST и PUT требуют оба поля name и price. Строковые числа, неизвестные поля и клиентский id отклоняются. PUT полностью заменяет name и price, не создавая отсутствующий товар.

| Запрос | Ответ |
|---|---|
| POST /items | 201, созданный товар |
| GET /items/{id} | 200, товар; 404, если отсутствует |
| PUT /items/{id} | 200, обновлённый товар; 404, если отсутствует |
| GET /health | 200, `{"status":"ok"}` |

Невалидное JSON-тело и нарушения схемы дают 400 без изменения хранилища. Ошибки содержат JSON-поле `message`. Неподдерживаемый Content-Type даёт 415.

```bash
curl -i -X POST http://127.0.0.1:18080/items \
  -H 'Content-Type: application/json' \
  -d '{"name":"Клавиатура","price":450000}'

# Подставьте id из ответа POST:
curl -i http://127.0.0.1:18080/items/ID
curl -i -X PUT http://127.0.0.1:18080/items/ID \
  -H 'Content-Type: application/json' \
  -d '{"name":"Мышь","price":150000}'
curl -i http://127.0.0.1:18080/items/missing
```

## Разработка и тесты

Node.js 24.21.0 (`nvm use` при установленном nvm) и pnpm 10.19.0. Версия pnpm закреплена в `package.json` и Dockerfile. Если pnpm ещё не установлен: `npm install --global pnpm@10.19.0`. Docker устанавливает его самостоятельно. Из `hw-1/`:

```bash
pnpm install --frozen-lockfile
pnpm run build
pnpm test
POD_ID=pod-1 DATACENTER=dc-1 pnpm start
```

Локальный процесс слушает порт 3000; переменная `PORT` переопределяет его. Остановка — Ctrl+C. Для перезапуска при изменении исходников:

```bash
POD_ID=pod-1 DATACENTER=dc-1 pnpm run dev
```

Четыре небольших HTTP-теста используют Fastify inject без открытого порта: жизненный цикл товара и 404, сбор Counter/Histogram, учёт ошибок 400/404/500, каталог /handlers и исключение служебных запросов из бизнес-метрик.

## Структура

- `src/app.ts` — сборка приложения, отдельный `/health`.
- `src/server.ts` — запуск и завершение процесса.
- `src/products.ts` — бизнес-ручки и схема запросов.
- `src/store.ts` — модель и Map-хранилище.
- `src/monitoring.ts` — реестр метрик, hooks, обнаружение ручек и экспорт.
- `tests/` — HTTP-проверки.

Память растёт с числом созданных товаров; автоматического удаления нет. Длительную нагрузку и её ограничения добавим отдельным этапом.

## Мониторинг

`POD_ID` и `DATACENTER` обязательны: отсутствие или значение из пробелов завершает запуск до открытия порта. Compose передаёт их каждой реплике из `POD_1_ID`/`DATACENTER_1` и `POD_2_ID`/`DATACENTER_2`. По умолчанию это pod-1/dc-1 и pod-2/dc-2. Для локального процесса вне Docker по-прежнему нужны `POD_ID` и `DATACENTER`.

| Метрика | Тип | Лейблы |
|---|---|---|
| `http_requests_total` | Counter | `method`, `route`, `pod_id`, `datacenter`, `status_code` |
| `http_request_duration_seconds` | Histogram | `method`, `route`, `pod_id`, `datacenter` |

Counter считает завершённые бизнес-ответы, включая 400, 404 и 500. Из него впоследствии вычисляются RPS и ошибки по кодам. Histogram содержит длительности в секундах; код ответа исключён ради меньшего числа рядов. `route` — шаблон `/items/:id`, без конкретных ID и query string. GET и PUT различаются `method`.

Бакеты Histogram: `0.001, 0.0025, 0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, +Inf` секунды. Бакеты накопительные: запрос 30 мс учитывается в 50 мс и всех больших границах. Одинаковые бакеты нескольких экземпляров можно сложить до расчёта p50/p95/p99. Готовые квантили Summary усреднять между репликами нельзя. Перцентили Histogram остаются оценкой с погрешностью внутри бакета.

Время измеряется монотонными часами от `onRequest` до `onResponse` после события `finish`, включая чтение тела, валидацию и отправку ответа сервером. Это серверная длительность, а не RTT клиента. Оборванные до завершения отправки ответы, неизвестные URL и служебные `/health`, `/metrics`, `/handlers` исключаются. 404 отсутствующего товара на зарегистрированной ручке учитывается.

```bash
curl http://127.0.0.1:18080/metrics
curl http://127.0.0.1:18080/handlers
```

`/metrics` возвращает Prometheus text format с соответствующим Content-Type; до первых запросов серии могут отсутствовать. `/handlers` возвращает:

```json
{"handlers":[{"method":"GET","path":"/items/:id"},{"method":"POST","path":"/items"},{"method":"PUT","path":"/items/:id"}]}
```

Для добавления бизнес-ручек регистрируйте их в бизнес-плагине, передаваемом в `createApp(identity, { businessRoutes })` (по умолчанию `productRoutes`). Hooks и каталог наследуются вложенными роутерами, включая префиксы. Ручные инкременты в обработчиках не нужны. Каждое приложение имеет свой реестр; служебные маршруты регистрируются вне бизнес-области.

## Два экземпляра и Prometheus

Оба API используют один образ `product-catalog-hw1-app:1.0.0`. Сборка выполняется для api-1; api-2 использует готовый локальный образ после готовности api-1. Prometheus 3.15.1 стартует после готовности обоих API. После старта сбор независим: отказ одного API не останавливает второй.

Prometheus опрашивает `api-1:3000/metrics` и `api-2:3000/metrics` внутри Docker каждые 5 секунд с timeout 3 секунды, job — `items-api`. Хост-порты на сбор не влияют. Конфигурация находится в `infra/prometheus/prometheus.yml` и монтируется read-only.

1. Откройте http://127.0.0.1:9090/targets и дождитесь двух целей UP.
2. Выполните бизнес-запросы на обоих API (например, GET `/items/missing`). До первых запросов бизнес-серии могут отсутствовать.
3. После следующего scrape в интерфейсе Query проверьте `up{job="items-api"}`, `http_requests_total` и `http_request_duration_seconds_bucket`. Метрики приложения различаются по pod_id/datacenter, все серии — также по instance.

Товар, созданный на первом API, отсутствует на втором. Направляйте чтение и обновление на экземпляр, который создал товар. Балансировщика нет.

```bash
# Проверка конфигурации:
docker compose config --quiet
docker compose run --rm --no-deps --entrypoint /bin/promtool prometheus check config /etc/prometheus/prometheus.yml
# Проверка отказа; затем обязательно восстановите реплику:
docker compose stop api-2
docker compose start api-2
```

История Prometheus хранится в именованном volume `prometheus-data`, retention — 2 дня или 1 GB, что наступит раньше. `docker compose down` сохраняет историю. Для просмотра прошлых значений выберите исторический диапазон в интерфейсе. Товары API при down/up теряются.

`docker compose down -v` дополнительно **удаляет историю Prometheus**. Используйте только если хотите очистить стенд. После изменения prometheus.yml выполните `docker compose restart prometheus`.

### Обновление прежнего одиночного стенда

При существующем `.env` перенесите API_PORT в API_1_PORT, POD_ID в POD_1_ID и DATACENTER в DATACENTER_1, добавьте остальные параметры из `.env.example`. Сохраните собственные порты. Для удаления прежнего orphan-сервиса api в этом Compose-проекте выполните `docker compose up -d --remove-orphans --wait` (без `-v`).

Если порт 9090 уже занят, задайте свободный PROMETHEUS_PORT и используйте его в адресах браузера. Имена сервисов в командах теперь `api-1`, `api-2`, `prometheus`.

## Grafana

После `make up` интерфейс доступен по http://127.0.0.1:3000 (порт меняется через `GRAFANA_PORT`). Начальные логин и пароль берутся из `GRAFANA_ADMIN_USER` и `GRAFANA_ADMIN_PASSWORD` в `.env`. Вход анонимно и самостоятельная регистрация отключены.

`.env.example` содержит публичные учебные demo-значения для запуска двумя командами. Локальный `.env` может содержать отдельный пароль; смотрите его в своём файле. Реальные пароли не коммитятся. При обновлении существующего `.env` добавьте три параметра Grafana из примера, сохранив собственные настройки остальных сервисов.

Datasource `Prometheus` создаётся автоматически из `infra/grafana/provisioning/datasources/prometheus.yml`:

- постоянный UID `items-prometheus`;
- адрес внутри Docker `http://prometheus:9090` (даже если на хосте порт 19090);
- источник по умолчанию, редактирование через UI отключено;
- scrape interval 5 секунд, как у Prometheus.

Для проверки войдите в Grafana, откройте **Explore**, выберите **Prometheus**, переключите запрос в режим Code и выполните `up{job="items-api"}`. Должны отображаться две серии со значением 1. Для метрик бизнес-ручек сначала отправьте запросы к API и подождите очередного scrape. Дашборда на этом этапе ещё нет.

Grafana ждёт готовности Prometheus и имеет healthcheck `/api/health`. Состояние сохраняется в отдельном `grafana-data`: обычные `make stop`, `make down` и `make rebuild` его не удаляют. После повторного запуска datasource обновляется с тем же UID без дубликатов.

Логин и пароль из окружения применяются **при создании новой базы Grafana**. Изменение пароля только в `.env` при существующем томе не меняет действующий пароль. Для обычной смены войдите в Grafana и измените пароль в профиле; затем обновите локальный `.env`, чтобы будущий генератор использовал актуальные credentials. Для восстановления доступа администратор может воспользоваться `grafana cli admin reset-admin-password` внутри контейнера; сначала ознакомьтесь с `docker compose exec grafana grafana cli admin reset-admin-password --help` и не публикуйте пароль в истории команд или логах.

`docker compose down -v` удаляет **оба тома: Grafana и историю Prometheus**. Эта команда не нужна для обычной смены пароля. После правок provisioning перезапустите Grafana: `docker compose restart grafana`.
