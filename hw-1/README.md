# simple-crud

Мини-сервис который работает c обьектом `item` следующей структуры:

```rust
pub struct NewItem {
    name: String,
    price: i64,
    sold: u32,
}
```

и `id` для каждой записи в дб, обьекты можно создавать, обновлять и читать по айди.
Удаление и батч-операции для слабаков.

## Как запустить

```sh
cp .env.example .env
docker compose up
```

Всё собирается и поднимается само: два экземпляра приложения, Prometheus, Grafana, генератор
дашборда и нагрузка. Образы пересобираются при каждом `up` (`pull_policy: build`), так что
изменения в коде подхватываются без `--build`.

Дальше открываем Grafana на <http://localhost:3000> и логинимся данными из `.env` (по умолчанию
`admin` / `change-me`). Дашборд **simple-crud: golden signals** уже будет там. Нагрузка
разгоняется примерно за 3 минуты, поэтому графики заполняются постепенно.

## Порты

Эти порты на хосте должны быть свободны:

| Порт | Что там                              |
| ---- | ------------------------------------ |
| 3000 | Grafana                              |
| 3001 | приложение `app-1` (`pod-1`, `dc-1`) |
| 3002 | приложение `app-2` (`pod-2`, `dc-2`) |
| 9090 | Prometheus                           |

Внутри контейнера приложение всегда слушает 3000. Метрики отдаются на `GET /metrics`, список
эндпоинтов для генератора дашборда на `GET /handlers`.

## Метрики и лейблы

Метрик всего две:

| Метрика                         | Тип       | Для чего                                   |
| ------------------------------- | --------- | ------------------------------------------ |
| `http_requests_total`           | counter   | RPS (`rate`) и ошибки (фильтр по `status`) |
| `http_request_duration_seconds` | histogram | latency: p50, p95, p99                     |

Лейблы у обеих одинаковые:

| Лейбл        | Откуда берётся                             | Пример        |
| ------------ | ------------------------------------------ | ------------- |
| `pod`        | переменная окружения `POD_ID`              | `pod-1`       |
| `datacenter` | переменная окружения `DATACENTER`          | `dc-1`        |
| `method`     | HTTP-метод                                 | `GET`         |
| `endpoint`   | шаблон пути из роутера, а не реальный путь | `/items/{id}` |
| `status`     | код ответа                                 | `404`         |

Отдельный счётчик ошибок не нужен: ошибки это те же запросы с `status=~"4..|5.."`, и разбивка по
кодам получается сама собой. В `endpoint` пишется именно шаблон, иначе каждый id давал бы новый
временной ряд и кардинальность бы улетела. Служебные `/health`, `/metrics` и `/handlers` не
меряются.

## Почему histogram для latency

У Prometheus для распределений есть два типа: summary и histogram.

Summary считает квантили прямо внутри процесса, и сложить их между подами нельзя: среднее из p99
двух подов не равно p99 всего сервиса. А у нас как раз несколько подов в разных датацентрах, и на
дашборде их надо агрегировать по выбранным значениям.

Histogram отдаёт обычные счётчики по бакетам (`_bucket{le="..."}`). Счётчики спокойно
складываются, поэтому сначала суммируем бакеты по всем выбранным подам и датацентрам, а квантиль
считаем уже на стороне Prometheus:

```promql
histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket{...}[$__rate_interval])))
```

Минус у histogram в том, что квантиль приблизительный: внутри бакета значение интерполируется.
Поэтому бакеты (от 0.5 мс до 10 с) сделаны частыми именно в миллисекундах, где и живёт этот
сервис. И ещё одна деталь: `metrics-exporter-prometheus` по умолчанию отдаёт summary, так что
бакеты задаются явно через `set_buckets_for_metric`.

## Что ещё стоит знать

- SQLite все ещё `in memory`. Присутсвие этой технологии не должно смущать читающего, данные все ещё храняться сторого
  в памяти, просто в `axum` я по работе привык хранить данные в нем и соответсвенно мне было проще из головы достать
  такую реализацию чем условно пихать хеш мапу в стейт. По факту реализации мало чем отличаются.
- **Ошибки в нагрузке.** Примерно 4% запросов заканчиваются ошибками: 404 (несуществующий id), 400
  (id не число), 422 (отрицательная цена) и 500. Пятисотки специально генерирует сам сервис:
  переменная `FAILURE_RATE` задаёт вероятность, с которой любой бизнесовый эндпоинт отвечает 500.
  По умолчанию 0, в compose стоит `0.01`. Поменять можно так: `FAILURE_RATE=0.05 docker compose up`.
- **Секреты.** Логин и пароль админа Grafana лежат только в `.env`, а он в `.gitignore`. Если их
  там нет, compose просто не запустится.
- **Дашборд не захардкожен.** Генератор берёт список эндпоинтов из `/handlers` при каждом запуске,
  а приложение собирает этот список из тех же вызовов, которыми регистрирует роуты. Новый эндпоинт
  появится на дашборде после перезапуска стека, генератор трогать не надо.
- **Данные в памяти.** У каждого экземпляра своя SQLite в памяти, после рестарта всё пропадает.
- **Если меняете SQL.** После правок запросов или миграций нужно выполнить `cargo sqlx prepare`,
  иначе Docker-сборка упадёт: она проверяет запросы по файлам в `.sqlx/`.
