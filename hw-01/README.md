# HW-01: метрики и генерация дашборда в Grafana

Микросервис `items-service` (FastAPI, in-memory CRUD), который отдаёт метрики latency, traffic и errors
по каждой бизнес-ручке, плюс Prometheus, Grafana, генератор дашборда и фоновый генератор нагрузки
в `docker-compose.yaml`.

## Запуск

```bash
cd hw-01
cp .env.example .env    # при желании поменяйте пароль Grafana
docker compose up --build
```

| Сервис     | Адрес                    | Что там                              |
|------------|--------------------------|--------------------------------------|
| app-1      | http://127.0.0.1:8081    | pod-1, dc-msk                        |
| app-2      | http://127.0.0.1:8082    | pod-2, dc-spb                        |
| Prometheus | http://127.0.0.1:9090    | скрейпит оба пода каждые 5 с         |
| Grafana    | http://127.0.0.1:3000    | логин/пароль из `.env`, дашборд ниже |
| dashboard-generator | — (one-shot)  | создаёт дашборд и завершается        |
| load-generator      | — (фон)       | разгоняет и держит нагрузку          |

Порты опубликованы только на `127.0.0.1`. Дашборд после запуска:
http://127.0.0.1:3000/d/items-service (uid `items-service`).

```bash
docker compose run --rm dashboard-generator   # пересоздать дашборд, не перезапуская стек
docker compose down                           # остановить стек
docker compose down -v                        # остановить и удалить данные Prometheus/Grafana
```

## Ручки сервиса

| Ручка                  | Описание                                    | Метрики |
|------------------------|---------------------------------------------|---------|
| `POST /items`          | создать запись → 201                        | да      |
| `GET /items/{item_id}` | получить запись → 200 / 404                 | да      |
| `PUT /items/{item_id}` | обновить запись → 200 / 404                 | да      |
| `GET /health`          | готовность (используется в healthcheck)     | нет     |
| `GET /metrics`         | метрики в формате Prometheus                | нет     |
| `GET /handlers`        | список бизнес-ручек для генератора дашборда | нет     |

Формат `GET /handlers` — ключи совпадают с лейблами метрик, `route` — шаблон пути:

```json
{"handlers": [{"method": "POST", "route": "/items"},
              {"method": "GET",  "route": "/items/{item_id}"},
              {"method": "PUT",  "route": "/items/{item_id}"}]}
```

## Переменные окружения

| Переменная               | По умолчанию в compose | Назначение                                                        |
|--------------------------|------------------------|-------------------------------------------------------------------|
| `POD_ID`                 | `pod-1` / `pod-2`      | номер пода (лейбл `pod_id`)                                       |
| `DATACENTER`             | `dc-msk` / `dc-spb`    | датацентр (лейбл `datacenter`)                                    |
| `FAIL_RATE`              | `0.03`                 | вероятность искусственного 500 на бизнес-ручке                    |
| `DELAY_MEAN_MS`          | `20`                   | средняя искусственная задержка бизнес-ручки, мс (0 — выключено)   |
| `GRAFANA_ADMIN_USER`     | из `.env`              | логин администратора Grafana                                      |
| `GRAFANA_ADMIN_PASSWORD` | из `.env`              | пароль администратора Grafana                                     |
| `TARGET_RPS`             | `40`                   | суммарный RPS после разгона (на оба пода)                         |
| `RAMP_SECONDS`           | `180`                  | за сколько секунд линейно разогнаться до `TARGET_RPS`             |
| `NOT_FOUND_RATE`         | `0.05`                 | доля GET/PUT к несуществующим id (даёт 404)                       |

Секреты лежат только в `.env`, который не попадает в git (`.gitignore`); в репозитории — `.env.example`.

## Метрики

Инструментирование — `app/metrics.py`. Используется свой класс роута `MetricsRoute(APIRoute)`:
он подключён только к роутеру с бизнес-ручками (`APIRouter(route_class=MetricsRoute)`),
поэтому `/health`, `/metrics` и `/handlers` в метрики не попадают без явных исключений в коде.
`setup_metrics(app)` регистрирует `/metrics` и `/handlers`; список для `/handlers` строится
по тому же признаку (`isinstance(route, MetricsRoute)`), что и инструментирование, поэтому
ручки на дашборде и ручки с метриками не могут разойтись.

| Метрика                  | Тип       | Лейблы                                              |
|--------------------------|-----------|-----------------------------------------------------|
| `latency_seconds`        | Histogram | `pod_id`, `datacenter`, `method`, `route`           |
| `requests_amount_total`  | Counter   | `pod_id`, `datacenter`, `method`, `route`, `status_code` |

- `pod_id`, `datacenter` — из `POD_ID` и `DATACENTER`.
- `method` + `route` — идентификатор ручки: HTTP-метод и **шаблон** пути (`/items/{item_id}`),
  а не фактический путь — иначе на каждый id появлялся бы новый временной ряд.
- `status_code` — код ответа. Коды 404/500 из `HTTPException` и 422 из ошибок валидации
  берутся из исключения, необработанное исключение учитывается как 500.

Что из этого строится:
- **RPS** — `rate` счётчика;
- **ошибки по кодам** — тот же счётчик с фильтром по `status_code` 4xx/5xx;
- **latency p50/p95/p99** — `histogram_quantile` по бакетам гистограммы.

`status_code` есть только у счётчика: в гистограмме он умножил бы число рядов на число кодов,
а latency по коду ответа для дашборда не требуется.

### Почему Histogram, а не Summary

Перцентили должны оставаться корректными при агрегации по нескольким подам.

- **Summary** считает квантили внутри процесса и отдаёт готовые числа. Квантили нельзя
  складывать или усреднять: p99 двух подов — это не среднее их p99.
- **Histogram** отдаёт счётчики попаданий в бакеты (`_bucket{le=...}`). Счётчики складываются,
  поэтому можно сначала просуммировать бакеты по выбранным подам и датацентрам
  (`sum by (le)`), а уже потом посчитать квантиль через `histogram_quantile`.

Условие корректности — одинаковые границы бакетов на всех подах; здесь оба пода из одного образа.

### Бакеты

```
5ms 10ms 20ms 30ms 50ms 75ms 100ms 150ms 250ms 500ms 1s 2.5s
```

Подобраны под модель latency сервиса (см. ниже, среднее 20 мс): основная масса запросов
лежит в 5–100 мс, где бакеты плотные, а p50/p95/p99 попадают в разные бакеты
(≈14 / 60 / 92 мс). Ошибка линейной интерполяции `histogram_quantile` для этих перцентилей —
в пределах ~6%. Хвост до 2.5 с оставлен, чтобы деградация была видна, а квантиль не упирался в `+Inf`.
Если сильно изменить `DELAY_MEAN_MS`, бакеты нужно пересмотреть.

### Модель latency и ошибок

- Бизнес-ручки «работают» `asyncio.sleep` со случайной задержкой из экспоненциального
  распределения со средним `DELAY_MEAN_MS`: большинство запросов быстрые, есть длинный хвост,
  поэтому p50, p95 и p99 заметно различаются.
- С вероятностью `FAIL_RATE` ручка отвечает 500; запросы к несуществующему id дают 404.

## Генератор дашборда

`generator/generate.py` (Python 3.13, только stdlib) запускается сервисом
`dashboard-generator` после health-проверок приложения и Grafana.

1. Читает список бизнес-ручек из `GET /handlers` — поэтому новые ручки появляются
   на дашборде без правок кода генератора.
2. Собирает JSON и делает `POST /api/dashboards/db` с `overwrite: true`
   (повторный запуск обновляет тот же дашборд).
3. Выходит с кодом 0 при успехе — на этом держится
   `depends_on: dashboard-generator: condition: service_completed_successfully`
   у нагрузчика.

Дашборд: uid `items-service`, заголовок «items-service»,
нередактируемый (`editable: false`), автообновление каждые 10 с.

`editable: false` — стандартный флаг Grafana: он убирает редактирование для
обычного пользователя. Администратор всё равно может сделать дашборд
редактируемым через UI/API (`canEdit: true`), так что это не защита от админа,
а выполнение требования «non-editable».

Переменные:

- `datacenter` — `label_values(requests_amount_total, datacenter)`, мульти-выбор + All;
- `pod_id` — `label_values(requests_amount_total{datacenter=~"$datacenter"}, pod_id)`,
  мульти-выбор + All.

`allValue` у обеих переменных — `.*`, поэтому «All» не сужает выборку. Для каждой
ручки (пара method + route) создаётся строка и три панели:

| Панель           | PromQL |
|------------------|--------|
| Latency p50/p95/p99 | `histogram_quantile(0.5/0.95/0.99, sum by (le) (rate(latency_seconds_bucket{route="…",method="…",datacenter=~"$datacenter",pod_id=~"$pod_id"}[$__rate_interval])))` |
| RPS              | `sum(rate(requests_amount_total{route="…",method="…",datacenter=~"$datacenter",pod_id=~"$pod_id"}[$__rate_interval]))` |
| Errors           | `sum by (status_code) (rate(requests_amount_total{…,status_code=~"[45][0-9][0-9]"}[$__rate_interval]))` |

Перцентили считаются поверх суммы бакетов по выбранным подам (`sum by (le)`),
а не как среднее перцентилей; `rate` тоже суммируется по выбранным подам и
датацентрам. Источник данных во всех запросах — `{type: prometheus, uid:
prometheus-main}` из provisioning.

## Нагрузка

`loadgen/load.py` (Python, stdlib, `ThreadPoolExecutor`) запускается сервисом
`load-generator` после `dashboard-generator` и работает до остановки стека.

- Линейный разгон с 0 до `TARGET_RPS` (по умолчанию 40 суммарно на оба пода) за
  `RAMP_SECONDS` (180 с), затем постоянная фоновая нагрузка.
- Запросы распределяются случайно по обоим подам и по всем ручкам:
  `POST /items`, `GET /items/{item_id}`, `PUT /items/{item_id}`.
- Запросы отправляются равномерно (пауза `1/rps`), а не пачками раз в секунду.
- Созданные id хранятся отдельно для каждого пода: у подов независимые in-memory
  хранилища, поэтому GET/PUT идут только к id, созданным на том же поде.
- 404: доля `NOT_FOUND_RATE` (5%) GET/PUT идёт к несуществующим id. Это примерно
  3.3% от всех запросов, так как GET и PUT вместе — две трети трафика.
- 500: приложение само отвечает 500 с вероятностью `FAIL_RATE` (3%).
- В итоге 404 и 500 вместе дают около 6% ошибок — «несколько процентов» по заданию;
  на дашборде видны оба кода.
- Пул ограничен 32 воркерами. Если сервис начнёт отвечать медленнее, очередь задач
  может расти; при штатной latency ~20 мс этого не происходит. Для длительной
  деградации стоит ограничивать in-flight запросы, но для фоновой нагрузки это
  осознанно опущено.

Ожидаемые 4xx/5xx не считаются ошибкой нагрузочного скрипта.

### Что видно после разгона

Замер по Prometheus через ~3.5 минуты после старта нагрузки (окно `rate` 1 мин):

| Показатель            | Значение                              |
|-----------------------|---------------------------------------|
| RPS суммарно          | ≈ 37–38 (цель 40)                     |
| RPS по подам          | pod-1 ≈ 19, pod-2 ≈ 17.5              |
| RPS по ручкам         | POST / GET / PUT ≈ 12 каждая          |
| Ошибки                | 404 ≈ 2.9%, 500 ≈ 2.7% (всего ≈ 5.6%) |
| Latency GET p50/p95/p99 | ≈ 20 / 70 / 90 мс                   |

RPS чуть ниже цели: пауза между запросами отсчитывается от предыдущего запроса,
и мелкие задержки цикла накапливаются.
