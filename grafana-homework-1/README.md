# NetInventory

Реестр оборудования учебной сети на Python и FastAPI. Сервис хранит карточки коммутаторов, маршрутизаторов и точек доступа, проверяет IP-адреса и позволяет изменять состояние устройства: `active`, `maintenance`, `disabled`.

Для каждого HTTP endpoint собираются время обработки, интенсивность запросов и ошибки. Prometheus получает метрики двух экземпляров приложения, а CLI-генератор создаёт дашборд Grafana по списку зарегистрированных обработчиков.

## Запуск

Требования: Docker Engine с Docker Compose либо Docker Desktop. Все команды выполняются из корня проекта. Python работает внутри контейнеров.

```bash
cp .env.example .env
```

До первого запуска в `.env` задаются `GRAFANA_ADMIN_USER` и `GRAFANA_ADMIN_PASSWORD`. Значение пароля в `.env.example` является примером. Локальный `.env` исключён из Git и контекста сборки Docker.

```bash
make up
```

Эквивалент без Make:

```bash
docker compose up -d --build
```

Образы собираются и загружаются при первом развёртывании. После запуска фоновой нагрузки для наполнения графиков требуется около трёх минут.

| Адрес | Назначение |
|---|---|
| [localhost:8001/health](http://localhost:8001/health) | Экземпляр `pod-1`, датацентр `dc-a` |
| [localhost:8002/health](http://localhost:8002/health) | Экземпляр `pod-2`, датацентр `dc-b` |
| [localhost:9090/targets](http://localhost:9090/targets) | Два источника метрик Prometheus |
| [localhost:3000/d/netinventory-api](http://localhost:3000/d/netinventory-api) | NetInventory / API health |

Порты опубликованы на `127.0.0.1`. Для входа в Grafana используются значения из `.env`.

## Модель устройства

```json
{
  "name": "lab-switch-01",
  "ip_address": "192.168.10.2",
  "kind": "switch",
  "state": "active"
}
```

| Поле | Ограничения |
|---|---|
| `name` | Непустая строка длиной до 120 символов; пробелы по краям удаляются |
| `ip_address` | Валидный IPv4 или IPv6 |
| `kind` | `switch`, `router`, `access_point` |
| `state` | `active`, `maintenance`, `disabled`; по умолчанию `active` |
| `id` | UUID, назначается сервером и возвращается в ответе |

Неизвестные поля запроса отклоняются. IP-адрес нормализуется перед сохранением: две записи одного IPv6-адреса в разных формах считаются одинаковыми.

`DeviceRegistry` хранит карточки и индекс IP → UUID в памяти процесса. Адрес уникален в пределах одного экземпляра. PUT заменяет карточку, сохраняет её UUID и может менять адрес. Проверка конфликта выполняется до изменения данных; неудачное обновление сохраняет прежнюю карточку. После успешной смены адреса старый адрес освобождается.

У двух экземпляров независимые реестры. POST, последующие GET и PUT для одной карточки отправляются на один адрес приложения. Перезапуск процесса удаляет его записи. Каждый контейнер запускает один процесс Uvicorn.

## HTTP API

Пути `/items` сохранены в соответствии со спецификацией задания; объектом API является сетевое устройство.

| Метод и путь | Действие | Ответы |
|---|---|---|
| `POST /items` | Регистрация устройства | `201`, `409`, `422` |
| `GET /items/{id}` | Получение карточки | `200`, `404` |
| `PUT /items/{id}` | Замена карточки или изменение состояния | `200`, `404`, `409`, `422` |
| `GET /health` | Готовность, название сервиса, pod и датацентр | `200` |
| `GET /handlers` | Список HTTP-методов и шаблонов бизнес-endpoints | `200` |
| `GET /metrics` | Метрики Prometheus | `200` |

404 означает отсутствие UUID, 409 — конфликт IP-адреса, 422 — ошибку валидации. При `DEMO_FAULTS=true` заголовок `X-Demo-Error: 500` вызывает управляемый серверный сбой у бизнес-endpoints.

Регистрация:

```bash
curl -i -X POST http://localhost:8001/items \
  -H 'Content-Type: application/json' \
  -d '{"name":"lab-switch-01","ip_address":"192.168.10.2","kind":"switch","state":"active"}'
```

Для следующих команд `DEVICE_ID` задаётся значением `id` из ответа POST:

```bash
DEVICE_ID='UUID_ИЗ_ОТВЕТА'
curl -i "http://localhost:8001/items/$DEVICE_ID"
curl -i -X PUT "http://localhost:8001/items/$DEVICE_ID" \
  -H 'Content-Type: application/json' \
  -d '{"name":"lab-switch-01","ip_address":"192.168.10.2","kind":"switch","state":"maintenance"}'
```

Повторный POST с тем же IP вернёт 409. Передача `"ip_address":"not-an-ip"` вернёт 422.

## Состав и порядок запуска

- `app-1`, `app-2`: два экземпляра образа `netinventory-api:1.0` с разными `POD_ID` и `DATACENTER`.
- `prometheus`: опрашивает `/metrics` обоих приложений каждые 5 секунд.
- `grafana`: получает источник Prometheus через provisioning, UID `prometheus-lab`.
- `dashboard-generator`: ожидает готовности приложений и Grafana, читает `/handlers`, отправляет JSON в Grafana HTTP API и завершается с кодом 0.
- `load-generator`: запускается после успешного завершения генератора дашборда и поддерживает фоновую нагрузку.

Проверки готовности заданы через `condition: service_healthy`, успешное завершение генератора — через `condition: service_completed_successfully`. `Exited (0)` у генератора является штатным состоянием.

Версии: Python 3.13.7, FastAPI 0.116.1, Uvicorn 0.35.0, prometheus-client 0.22.1, Prometheus 3.6.0, Grafana 12.2.0. Название Compose project `itmo-grafana-lab` сохраняет совместимость с локальными volumes предыдущего развёртывания.

## Метрики

Обёртка `MonitoredRoute` измеряет длительность через `perf_counter()` и в `finally` фиксирует результат, включая HTTP-исключения и ошибки валидации. `/health`, `/handlers` и `/metrics` исключены из бизнес-метрик.

| Метрика | Тип | Labels |
|---|---|---|
| `netinventory_http_requests_total` | Counter | `pod_id`, `datacenter`, `method`, `route`, `status_code` |
| `netinventory_request_duration_seconds` | Classic Histogram | `pod_id`, `datacenter`, `method`, `route` |

`route` содержит шаблон `/items/{id}`, поэтому UUID карточек не увеличивают число временных рядов. IP-адреса и названия устройств в labels не включаются.

Histogram экспортирует накопительные бакеты с границами 5, 10, 20, 30, 50, 75, 100, 150, 250, 500 мс, 1 и 2.5 с, а также `+Inf`. Для объединения экземпляров сначала вычисляется rate бакетов и сумма по `le`, затем перцентиль. Усреднение отдельных p99 не даёт p99 общего распределения; точность оценки зависит от ширины бакетов.

Примеры для `GET /items/{id}`:

```promql
# RPS выбранного endpoint по всем экземплярам.
sum(rate(netinventory_http_requests_total{method="GET",route="/items/{id}"}[1m]))

# Ошибки в секунду по конкретному коду.
sum by (status_code) (
  rate(netinventory_http_requests_total{
    method="GET",route="/items/{id}",status_code=~"4..|5.."
  }[1m])
)

# Общий p99 двух экземпляров.
histogram_quantile(0.99,
  sum by (le) (
    rate(netinventory_request_duration_seconds_bucket{
      method="GET",route="/items/{id}"
    }[1m])
  )
)
```

Для p50 и p95 используются 0.5 и 0.95. `rate` применяется до суммирования, чтобы учитывать сброс счётчика отдельного процесса.

## Дашборд

Генератор объединяет пары метод/путь из `/handlers` обоих приложений без дубликатов. Для каждого endpoint создаёт панели latency с p50/p95/p99, RPS и ошибок по HTTP-кодам. Ещё две панели показывают суммарный RPS и распределение по экземплярам — всего 11 панелей.

Список endpoints в генераторе не задан статически. Новый обработчик в роутере с `MonitoredRoute` появляется в `/handlers` и получает панели при следующем запуске генератора.

Дашборд сохраняется через `POST /api/dashboards/db` с UID `netinventory-api`, `overwrite: true` и `editable: false`. Селекторы `Datacenter` и `Pod` поддерживают несколько значений и `All`. PromQL использует `${datacenter:regex}`, `${pod_id:regex}` и `[$__rate_interval]`; обновление выполняется каждые 5 секунд.

## Сценарий нагрузки

Генератор создаёт тестовое устройство на каждом экземпляре. Затем распределяет запросы между регистрацией новых устройств, чтением карточек и переходами состояния `active` → `maintenance` → `disabled`. Для успешных GET/PUT используется UUID из реестра того же экземпляра. Новые устройства получают случайные IPv6-адреса из локального диапазона `fd10::/16`; каждый запуск использует новые адреса.

Нагрузка растёт от 3 до 30 RPS суммарно за 120 секунд. За полный цикл 2% запросов вызывают 500, ещё 3% — клиентские ошибки: 404 для отсутствующих устройств, 409 для повторных адресов, 422 для некорректных IP. На коротких окнах доля ошибок колеблется из-за их группировки внутри цикла.

В модель обработки добавлено асинхронное ожидание 5–50 мс, примерно в 4% случаев — ещё 100 мс. Latency включает это ожидание и серверную обработку, но не передачу ответа по сети.

## Проверки и конфигурация

`make test` проверяет правила реестра, нормализацию IPv6, сохранность данных при конфликте и расширяемость генерации панелей. `make check` после разгона проверяет реальные HTTP-ответы, оба target Prometheus, источник данных, параметры дашборда, результаты всех PromQL-запросов и равенство общего RPS сумме экземпляров. Успешное завершение — `ALL CHECKS PASSED`.

| Переменная `.env` | Назначение / значение по умолчанию |
|---|---|
| `GRAFANA_ADMIN_USER`, `GRAFANA_ADMIN_PASSWORD` | Учётные данные администратора |
| `GRAFANA_PORT`, `PROMETHEUS_PORT` | `3000`, `9090` |
| `APP1_PORT`, `APP2_PORT` | `8001`, `8002` |
| `TARGET_RPS` | `30` суммарно |
| `RAMP_SECONDS` | `120` |
| `DEMO_FAULTS` | `true` |

Для проверки используются `DEMO_FAULTS=true` и установившаяся нагрузка 20–50 RPS. Адреса приложений и Grafana внутри сети Compose задаются через `APP_URLS` и `GRAFANA_URL`.

## Обслуживание

`make down` сохраняет настройки Grafana и историю Prometheus в named volumes. Время хранения метрик — 24 часа. `docker compose down -v` удаляет volumes вместе с этими данными.

После перезапуска приложения нагрузочный генератор запускается заново для создания актуальной тестовой карточки:

```bash
docker compose restart load-generator
```

Пароль Grafana из окружения применяется при инициализации её хранилища. Изменение `.env` не заменяет пароль в существующей базе; после смены пароля то же значение записывается в `.env` для доступа генератора к API.
