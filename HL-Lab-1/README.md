# Сервис Items

Небольшой CRUD-сервис на Go. Данные хранятся в памяти, метрики собирает Prometheus, а Grafana показывает их на дашборде.

## Запуск

Скопируйте пример настроек и задайте пароль администратора Grafana в `.env`:

```sh
cp .env.example .env
```

Запустите сервисы:

```sh
docker compose up --build
```

Откройте:

- API: <http://localhost:8080>
- Prometheus: <http://localhost:9090>
- Grafana: <http://localhost:3000>

Для входа в Grafana используйте логин и пароль из `.env`. 

Запускаются два экземпляра приложения: `items-1` в `dc-a` и `items-2` в `dc-b`. На компьютере доступен `items-1` по порту `8080`; второй экземпляр доступен только другим контейнерам.

Генератор дашборда ждёт, пока приложение и Grafana будут готовы. Затем он получает список маршрутов через `GET /handlers` и создаёт дашборд. Список маршрутов не записан в генераторе: новые маршруты появятся на дашборде после перезапуска стека.

После создания дашборда запускается генератор нагрузки. Он обращается к обоим экземплярам и использует все три CRUD-маршрута. Нагрузка растёт примерно с 1 до 45 запросов в секунду за три минуты, а затем держится на этом уровне до остановки стека.

Каждый 40-й запрос ищет несуществующую запись и получает `404`. Кроме того, каждый `PUT` имеет вероятность 5% завершиться искусственной ошибкой `500` (`INJECT_500_PROBABILITY=0.05`). В сумме это примерно 1,7% ответов `500` и 2,5% ответов `404`. Если переменная не задана, искусственные `500` отключены.

## API

- `GET /health` — сообщает, что приложение готово принимать запросы.
- `POST /items` — создаёт запись из JSON `{"name":"example","value":"data"}`. Возвращает запись с новым UUID и код `201`.
- `GET /items/{id}` — возвращает запись или `404`, если её нет.
- `PUT /items/{id}` — заменяет поля записи `name` и `value`. Возвращает `404`, если записи нет.
- `GET /handlers` — возвращает список маршрутов, которые собирают метрики.
- `GET /metrics` — отдаёт метрики Prometheus.

Данные хранятся только в памяти и пропадают после остановки приложения. Некорректный JSON приводит к ответу `400`, а тело запроса больше 1 МиБ — к `413`.

## Метрики и дашборд

Приложение отдаёт две основные метрики:

- `http_server_requests_total` — количество запросов.
- `http_server_request_duration_seconds` — длительность запросов.

У обеих метрик есть лейблы:

- `handler` — метод и шаблон пути, например `GET /items/{id}`.
- `pod_id` — значение `POD_ID`.
- `datacenter` — значение `DATACENTER`.
- `status_code` — HTTP-код ответа.

`POD_ID` и `DATACENTER` обязательны при запуске. Для `items-1` заданы `items-1` и `dc-a`, для `items-2` — `items-2` и `dc-b`. Служебные `/health`, `/metrics` и `/handlers` не попадают в метрики ручек.

### Как считаются latency и RPS

Для длительности запросов используется Prometheus histogram с границами от 5 миллисекунд до 10 секунд. Она хранит число запросов, попавших в каждый временной диапазон.

Histogram выбрана потому, что данные из нескольких экземпляров можно сложить, а затем посчитать перцентили. Поэтому дашборд сначала объединяет бакеты выбранных подов и датацентров, сохраняя метку границы `le`, и затем применяет `histogram_quantile()`. Например:

```promql
histogram_quantile(0.95, sum by (le) (rate(http_server_request_duration_seconds_bucket[5m])))
```

Если сначала считать перцентили отдельно на каждом экземпляре, правильно объединить их потом нельзя. Поэтому здесь используется histogram, а не summary с готовыми значениями квантилей.

RPS считается как скорость роста счётчика запросов, сложенная по выбранным экземплярам:

```promql
sum(rate(http_server_requests_total[5m]))
```

В дашборде вместо фиксированных `5m` используются окна Grafana, чтобы расчёт подстраивался под выбранный период.

### Ошибки

Ответы с кодами `4xx` и `5xx` показываются по ручкам и кодам. Графики ручек показывают число ошибок в скользящем окне Grafana; сводка и таблица — число ошибок за весь выбранный на дашборде период. Для расчёта используется `increase()` — оценка прироста счётчика. Она иногда показывает дробное число, например `0.7`, хотя запросы считаются целыми. Это ожидаемо: Prometheus оценивает прирост на границах окна, которые обычно не совпадают со временем сбора метрик.

Вверху дашборда находятся общий RPS, p95 latency и число ошибок. Ниже — общая таблица ошибок и графики каждой ручки: p50/p95/p99, RPS и ошибки по кодам. Фильтры `Datacenter` и `Pod` позволяют выбрать несколько значений или `All`. Данные обновляются каждые 30 секунд, по умолчанию показаны последние 15 минут. Пустой график ошибок означает, что за выбранное время ошибка не наблюдалась.

Datasource Prometheus создаётся автоматически и имеет UID `prometheus`. Дашборд имеет UID `items-golden-signals` и отключён для редактирования.
