# Домашняя работа 2/3. Kafka

## Запуск инфраструктуры

Запустите стенд из каталога `homework2`.

```sh
docker compose up -d
docker compose ps
docker compose logs kafka-init
```

Когда `kafka-init` напечатает `Kafka topics are ready.`, топики готовы. После этого контейнер завершится с кодом `0`. У PostgreSQL дождитесь статуса `healthy` в `docker compose ps`.

| Сервис | Из сети Compose | С хоста |
|---|---|---|
| Kafka | `kafka-1:19092,kafka-2:19092,kafka-3:19092` | `localhost:29092,localhost:39092,localhost:49092` |
| PostgreSQL | `postgresql://homework:homework@postgres:5432/kafka_homework` | `postgresql://homework:homework@localhost:15432/kafka_homework` |

Можно проверить топики и PostgreSQL следующими командами.

```sh
docker compose exec -T kafka-1 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka-1:19092 --describe
docker compose exec -T postgres psql -U homework -d kafka_homework -c 'SELECT 1;'
```

В выводе ожидаются events и events.dlt с тремя партициями и коэффициентом репликации 3. Для events также должно отображаться min.insync.replicas=2.

С хоста Kafka можно проверить через `kcat`.

```sh
kcat -b localhost:29092,localhost:39092,localhost:49092 -L
```

`docker compose down` останавливает стенд. Тома сохраняют данные между запусками.

## Запуск продюсеров и консьюмеров

С профилем `pipeline` запускаются три продюсера (`producer`, `producer-2`, `producer-3`) и три консьюмера (`consumer`, `consumer-2`, `consumer-3`). Образ собран на userver 3.2 для `linux/amd64`. На Apple Silicon переменная `QEMU_GUEST_BASE` нужна, чтобы `jemalloc` работал под QEMU.

```sh
docker compose --profile pipeline build producer
docker compose --profile pipeline up -d
docker compose --profile pipeline ps
```

Параметры передаются окружением Compose. Например, `EVENTS_PER_SECOND=20 PROCESSING_DELAY_MS=10 docker compose --profile pipeline up -d` задаёт скорость и задержку для всех экземпляров.

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `EVENTS_PER_SECOND` | `10` | Целевая скорость каждого продюсера |
| `KEY_MODE` | `user_id` | Ключ `user_id` или отправка без ключа с `none` |
| `PROCESSING_DELAY_MS` | `20` | Задержка одной попытки обработки |

Каждый продюсер генерирует события для 12 пользователей со своим префиксом. После перезапуска у продюсера появляется новый набор пользователей, и у каждого `seq` начинается с 1. Примерно у 2% событий стоит `payload.poison=true`. Продюсер ждёт подтверждения Kafka (`acks=all`), а `enable.idempotence=true` защищает от дублей при внутренних повторах клиента. При `SIGTERM` продюсер дожидается завершения текущей отправки.

Все консьюмеры работают в группе `events-processor`. Если у группы ещё нет сохранённого оффсета, они читают с начала доступных записей (`earliest`). Консьюмер коммитит оффсет следующего события после записи в PostgreSQL или подтверждения отправки в DLT. Если запись или отправка не удалась, он повторяет попытку с тем же событием. Перед штатной передачей партиции консьюмер фиксирует, до какого оффсета успел обработать события.

Если все три попытки обработки закончились ошибкой, консьюмер отправляет событие в `events.dlt`. В заголовках остаются причина ошибки и исходная позиция события (`error-reason`, `original-topic`, `original-partition` и `original-offset`). Успешно обработанные события попадают в `processed_events`. Повторы определяются по `event_id`, а их число хранится в `sink_counters`.

```sh
docker compose exec -T postgres psql -U homework -d kafka_homework \
  -c "SELECT value AS duplicates FROM sink_counters WHERE name = 'duplicates';"
docker compose exec -T kafka-1 /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server kafka-1:19092 --describe --group events-processor
```

Остановить весь стенд можно командой `docker compose --profile pipeline down`.

## Эксперименты под нагрузкой

### 1. Аварийная остановка консьюмера

**Гипотеза.** Думаю, после остановки консьюмера его партиция ненадолго перестанет обрабатываться. Потом её подхватит другой консьюмер и продолжит с последней сохранённой позиции. Если первый консьюмер успел записать событие в базу, но ещё не сохранил позицию в Kafka, это событие может прийти повторно. Ожидаю, что повтор отсеется по `event_id`, а `verify` покажет ноль пропусков.

Я выставил 24 события в секунду на продюсер и задержку обработки 50 мс. Затем выполнил `docker compose --profile pipeline kill -s SIGKILL consumer-3`. Контейнер завершился с кодом `137`. На этот момент сохранённый оффсет партиции 2 был `64`. После ребаланса эту партицию взял `consumer-2` и начал читать с `64`.

После запуска `consumer-3` я дождался, пока группа дочитает очередь. `verify` насчитал 1 551 запись в PostgreSQL и 25 в DLT. Вместе это 1 576 событий, столько же получилось по конечным оффсетам трёх партиций (`542 + 656 + 378`). База отбросила один дубль. Пропусков и нарушений порядка не было.

### 2. Последовательная остановка двух брокеров

**Гипотеза.** Думаю, после остановки первого брокера у партиций, где он был лидером, появится новый лидер. Двух оставшихся копий должно хватить для подтверждения записи, потому что в настройках минимум две синхронизированные реплики.

В этом прогоне я выставил 15 событий в секунду на продюсер и задержку обработки 20 мс.

1. Остановил первый брокер командой `docker compose stop kafka-1`. Лидером партиции 1 вместо брокера 1 стал брокер 2. В каждой партиции осталось по две синхронизированные реплики (ISR). Этого хватило для записи при `acks=all` и `min.insync.replicas=2`. Контрольная отправка вернула UUID и код `0`. Консьюмеры продолжили читать, лаг держался в пределах 0–3 событий.
2. Остановил второй брокер командой `docker compose stop kafka-2`. Одного брокера не хватило ни для кворума KRaft, ни для подтверждения записи в `events`. Контрольная отправка завершилась по тайм-ауту с кодом `1`. Продюсеры писали ошибки в лог и повторяли попытки. Число строк в PostgreSQL за время замера осталось `1 319`.
3. Вернул оба брокера командой `docker compose start kafka-1 kafka-2`. В ISR каждой партиции снова было по три реплики. Контрольная отправка снова вернула UUID и код `0`. Когда лаг упал до нуля, `verify` насчитал 2 307 записей в PostgreSQL и 41 в DLT. Пропусков, дублей и нарушений порядка не было.

### 3. Сравнение `KEY_MODE=user_id` и `KEY_MODE=none`

**Гипотеза.** С ключом `user_id` события одного пользователя должны попадать в одну партицию и обрабатываться по порядку. Без ключа они могут попасть в разные партиции. Тогда один консьюмер может успеть обработать `seq=2`, пока другой ещё занят с `seq=1`. Поэтому ожидаю ноль нарушений порядка с ключом и хотя бы одно без ключа. После обработки всей очереди в обоих прогонах ожидаю ноль пропусков.

В обоих прогонах я запустил по три продюсера и три консьюмера с одинаковыми настройками (`EVENTS_PER_SECOND=36` и `PROCESSING_DELAY_MS=60`). Пока продюсеры отправляли события, лаг рос. Результаты снял после того, как консьюмеры дочитали очередь.

| Ключ | Строки PostgreSQL | Записи DLT | Пропуски `seq` | Отброшенные дубли | Нарушения порядка |
|---|---:|---:|---:|---:|---:|
| `user_id` | 1 280 | 26 | 0 | 0 | 0 |
| `none` | 1 292 | 18 | 0 | 0 | 233 |

С ключом `verify` показал ноль нарушений порядка. Без ключа получилось 233 нарушения, поэтому `verify` завершился с кодом `1`. Например, у одного пользователя событие с `seq=2` из партиции 1 записалось в PostgreSQL раньше, чем `seq=1` из партиции 0. Пропусков в обоих прогонах не было, если учитывать события в DLT.
