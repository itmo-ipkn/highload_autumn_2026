# highload-lab

ДЗ №1: CRUD-сервис на Kotlin и Spring Boot, метрики Prometheus, генератор дашборда Grafana и скрипт нагрузки на Kotlin.
У каждого экземпляра приложения своё хранилище в памяти, при перезапуске записи теряются.

## Запуск

Нужны Docker и Docker Compose. Первый запуск из корня репозитория:

```bash
cd highload-lab
cp .env.example .env
docker-compose up
```

Compose соберёт приложения, запустит мониторинг, создаст дашборд и включит нагрузку. Логин и пароль Grafana берутся из `GRAFANA_ADMIN_USER` и `GRAFANA_ADMIN_PASSWORD` в `.env`. Этот файл исключён из Git.

| Сервис | Адрес на компьютере |
| --- | --- |
| `app-1`, датацентр `dc-1` | http://localhost:8081 |
| `app-2`, датацентр `dc-2` | http://localhost:8082 |
| Prometheus | http://localhost:9090 |
| Grafana | http://localhost:3000 |

[Дашборд Highload lab](http://localhost:3000/d/highload-lab-generated/highload-lab) создаётся автоматически по списку из `/handlers`. Для каждой ручки есть RPS, ошибки по кодам и latency p50/p95/p99. Селекторы датацентра и пода поддерживают несколько значений и All.

Остановка из той же папки: `docker-compose down`. После изменения кода запускайте `docker-compose up --build`.

## Метрики

Используются встроенные HTTP-метрики Spring Boot Actuator через Micrometer. Названия метрик оставлены стандартными. Prometheus опрашивает оба экземпляра раз в 5 секунд.

| Метрика | Назначение |
| --- | --- |
| `http_server_requests_seconds_count` | Число запросов. `rate` даёт RPS, фильтр по `status` — ошибки |
| `http_server_requests_seconds_bucket` | Накопительные счётчики запросов по границам длительности. Используются для перцентилей |
| `http_server_requests_seconds_sum` | Суммарная длительность запросов в секундах |

Из стандартных лейблов HTTP-метрик удалены `outcome`, `error` и `exception`, так как они не нужны для задания.

Лейблы:

- `pod_id`, `datacenter` — из переменных `POD_ID` и `DATACENTER`.
- `method` — HTTP-метод.
- `uri` — шаблон пути, например `/items/{id}`.
- `status` — код ответа.
- `le` — верхняя граница бакета в секундах. Есть только у `_bucket`.

Prometheus добавляет `job` и `instance`. Служебные `/health`, `/metrics`, `/handlers` исключены из HTTP-статистики.

Для latency выбрана **гистограмма**: бакеты с одинаковыми границами можно складывать по экземплярам. Перцентили считаются через `histogram_quantile` поверх `sum by (le)` от `rate` бакетов выбранных подов и датацентров. Готовые перцентили отдельных экземпляров усреднять нельзя. Для RPS значения `rate` суммируются, для ошибок сохраняется разбивка по `status`.

## Нагрузка

Генератор нагрузки стартует после готовности обоих приложений и успешного завершения генератора дашборда. За 120 секунд он повышает целевую нагрузку с 2 до 39 RPS суммарно на оба экземпляра, затрагивает три ручки и работает до остановки стека. Цель и время разгона задаются в `.env`: `LOAD_TARGET_RPS` и `LOAD_INCREASE_SECONDS`.

По умолчанию сервис добавляет задержку 20–200 мс и с общей вероятностью 5% возвращает `500` или `503`. Эти параметры задаются через `SIMULATION_MIN_DELAY_MS`, `SIMULATION_MAX_DELAY_MS`, `SIMULATION_ERROR_PROBABILITY`. Дополнительно 5% GET-запросов генератора нагрузки идут за несуществующей записью для получения `404`.

## HTTP API

- `POST /items` — создать запись. Тело `{"name":"example"}`, ответ содержит `id` и `name`.
- `GET /items/{id}` — получить запись. Для отсутствующего `id` возвращается `404`.
- `PUT /items/{id}` — обновить запись. Тело `{"name":"new name"}`.
- `GET /health` — проверка готовности приложения.
- `GET /metrics` — метрики в формате Prometheus.
- `GET /handlers` — список бизнес-ручек с HTTP-методами и шаблонами путей.
