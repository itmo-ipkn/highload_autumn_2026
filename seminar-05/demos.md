# Демонстрации: команды, прогноз, проверка

Если начинаете с этого файла, выполните раздел «Запуск на своём компьютере».
Если уже запустили стенд по `README.md`, получили успешный `READY` от проверки
и не останавливали сервер, переходите сразу к разделу **A**. Повторно запускать
сервер и устанавливать зависимости не нужно.

## Запуск на своём компьютере

Откройте в терминале папку, где находится этот файл, `requirements.txt`
и `compose.yaml`. Все команды ниже выполняются из этой папки.
Выберите один вариант запуска: Python или Docker. Они используют одинаковые
порты, поэтому перед сменой варианта остановите предыдущий (раздел «Остановка»).

### Вариант 1. Python 3.12

Нужен установленный Python 3.12. На Windows выполняйте команды в WSL2.
Для первой установки зависимостей нужен интернет.

**Терминал 1 — установка и запуск:**

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python tools/generate.py
.venv/bin/python app/server.py native
```

Выполняйте команды по очереди; при ошибке остановитесь на ней.
Последняя команда запускает серверы и остаётся работать. Дождитесь строки:

```text
READY native; Ctrl-C stops this process
```

Оставьте этот терминал открытым.

**Терминал 2 — проверка готовности:** откройте второй терминал в той же папке.

```bash
sh tools/check.sh
```

При успешной проверке появится:

```text
READY: origin, two HTTP replicas, HTTP gateway, gRPC, TCP gateway
```

Теперь переходите к разделу **A** ниже. Все команды опытов выполняйте
в терминале 2; в терминале 1 продолжает работать сервер.

### Вариант 2. Docker

Запустите Docker Desktop или Docker Engine. Нужен Docker Compose v2
с поддержкой `--wait`; Python на компьютере для этого варианта не нужен.
Используйте один терминал в папке семинара:

```bash
docker compose build
docker compose up -d --wait
docker compose run --rm client check
```

Выполняйте команды по очереди. После успешной проверки появится та же строка
`READY: origin, two HTTP replicas, HTTP gateway, gRPC, TCP gateway`.
Контейнеры работают в фоне; переходите к разделу **A** в этом же терминале.
В каждой команде ниже замените `.venv/bin/python tools/demo.py`
на `docker compose run --rm client`. Например, первый опыт:

```bash
docker compose run --rm client contracts --step http
```

При ошибке запуска или проверки воспользуйтесь разделом «Если что-то не работает»
в [README.md](README.md). До успешной проверки к опытам не переходите.

## Как выполнять опыты

Запускайте команды по одной, сначала предполагая результат, затем сравнивая
его с выводом. Одновременно два опыта не запускайте: они изменяют общие данные.

Числа задержки и порядок первой выбранной реплики зависят от среды. Проверяем
перечисленные ниже признаки.

## A. Контракт и наблюдаемый результат

### HTTP-представление

```bash
.venv/bin/python tools/demo.py contracts --step http
```

До запуска: какие части ответа описывают товар, а какие работу инфраструктуры?

После: `HTTP 200`, `price_rub: 1200`, `version: 1`, `X-Backend: backend-a`,
`X-Cache: BYPASS`, ETag `"book-1-v1"`. Сумма целая, в рублях; это выбор
нашего контракта, а не правило для всех денежных API.

### Тот же товар через gRPC

```bash
.venv/bin/python tools/demo.py contracts --step grpc
```

До запуска: изменились ли бизнес-данные от выбора транспорта?

После: protobuf-ответ с `item`, `served_by`, `cache`; проверка совпадения
`id`, цены и версии печатает `PASS`. Загляните в `proto/catalog.proto`:
типизированный метод и номера полей образуют контракт. Мы не сравниваем RPS.

### Проверка версии через ETag

```bash
.venv/bin/python tools/demo.py contracts --step conditional
```

До запуска: что вернёт сервер, если представление не изменилось?

После: первый ответ `200`, второй `304`, `<empty body>`, `origin_reads: 2`.
Клиент должен использовать свою ранее сохранённую копию. Источник в нашей
реализации всё равно читался: отсутствие тела не означает отсутствие работы.

### Ошибка предметной области

```bash
.venv/bin/python tools/demo.py contracts --step errors
```

До запуска: является ли отсутствие товара сетевой ошибкой?

После: HTTP `404` и gRPC `NOT_FOUND`. Это два способа сообщить одинаковую
бизнес-ситуацию. Не следует считать каждый транспортно успешный HTTP/2 ответ
успешным RPC: gRPC имеет отдельный статус.

### Deadline

```bash
.venv/bin/python tools/demo.py contracts --step deadline
```

До запуска: источник занимает 500 мс, клиент готов ждать 50 мс. Кто закончит
первым и что произойдёт с работой на источнике?

После: `DEADLINE_EXCEEDED`, время около 50 мс, а не строго 50. Затем скрипт
ждёт ещё 0,6 секунды. Завершение работы источника этим выводом не измеряется.
Отмена не откатывает выполненную работу. Retry,
распределение общего бюджета и backpressure подробно относятся к W7.

## B. Единица балансировки

### HTTP round robin

```bash
.venv/bin/python tools/demo.py balance --step http
```

Один клиент сохраняет одно HTTP/1.1-соединение с gateway и делает шесть
последовательных запросов. В списке появятся `backend-a` и `backend-b`.
Gateway принимает решение на каждый HTTP-запрос. В native-варианте это
Python-прокси, в Docker — nginx. Первый выбранный backend не фиксируем.

### Долгоживущий gRPC-канал за L4

```bash
.venv/bin/python tools/demo.py balance --step grpc-l4
```

Прогноз: распределятся ли шесть RPC так же, если TCP gateway выбрал backend
один раз? В результате все шесть имён одинаковы. Прокси пересылает реальные
байты одного TCP-соединения, внутри которого gRPC использует HTTP/2.
L4 не выбирает endpoint заново для каждого RPC. Это свойство данной схемы,
а не утверждение, что gRPC невозможно балансировать.

### Выбор endpoint на стороне клиента

```bash
.venv/bin/python tools/demo.py balance --step grpc-rr
```

Клиент получает два адреса и использует политику gRPC `round_robin`.
После прогрева обоих соединений в восьми результатах встречаются обе реплики.
Мы изменили место выбора backend. В production адреса должны приходить
из service discovery; здесь список явно задан. Альтернатива — L7 gRPC proxy,
который понимает границы RPC; такой прокси в данном стенде не запускается.

## C. Цена свежести

В этом блоке читаем backend-a напрямую, чтобы смена реплики не смешалась
с эффектом кэша. Каждый шаг сам сбрасывает цену, версию и кэши.

### Холодный и повторный запрос

```bash
.venv/bin/python tools/demo.py cache --step cold
```

Результат: `MISS`, затем `HIT`, оба ответа с ценой 1200, `origin_reads: 1`.
Отсутствие второго обращения к origin — измеряемый эффект. Из этих двух
запросов нельзя вывести production p99 или пропускную способность.

### Обновление источника

```bash
.venv/bin/python tools/demo.py cache --step stale
```

После заполнения кэша источник меняет цену на 1500, версию на 2. Кэш пока
возвращает 1200/1, прямое чтение с `cache=none` — 1500/2. Обновление источника
само по себе не изменяет копию в кэше.

### Явная инвалидация

```bash
.venv/bin/python tools/demo.py cache --step invalidate
```

Шаг заново заполняет кэш backend-a, обновляет origin и отправляет команду
инвалидации обеим репликам. Следующее чтение backend-a — `MISS`, цена 1500,
версия 2. Вторая копия в этом шаге не прогревается и не проверяется чтением.
Доставка событий инвалидации в реальной системе — отдельная задача.

### Истечение TTL

```bash
.venv/bin/python tools/demo.py cache --step ttl
```

Шаг заполняет кэш, обновляет origin и ждёт 3,2 секунды. TTL равен 3 секундам.
После ожидания `MISS`, цена 1500, версия 2. TTL ограничивает время жизни данной
записи с момента заполнения; бизнес-требование к свежести нужно задать раньше.

### Одновременные промахи

```bash
.venv/bin/python tools/demo.py cache --step stampede
```

Две серии по 12 клиентов стартуют на холодном кэше одной реплики. Чтение
источника искусственно занимает 500 мс. В `naive` получаем `origin_reads > 1`
(часто 12). В `singleflight` — ровно 1, один `MISS`, остальные `COALESCED`
или `HIT`, если поток стартовал позже. Это защита одного экземпляра кэша.
Ожидающие запросы не становятся бесплатными: они занимают ресурсы и ждут.

## Проверка всех сценариев

```bash
.venv/bin/python tools/demo.py check
.venv/bin/python tools/demo.py all
.venv/bin/python tools/demo.py reset
```

Если assertion не прошёл, сначала проверьте отсутствие параллельных клиентов
и повторите конкретный шаг.

## Остановка

Для Python нажмите `Ctrl-C` в терминале 1. Для Docker выполните:

```bash
docker compose down
```
