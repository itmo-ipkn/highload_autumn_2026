# HW2. Очередь Kafka

Модельное решение: кластер Kafka из 3 брокеров (KRaft), продюсеры и консьюмеры
с гарантией at-least-once, dead letter topic, идемпотентным sink (Postgres)
и мониторингом в Grafana.

## Состав

- **Kafka**: 3 брокера в режиме KRaft (`apache/kafka`), автосоздание топиков отключено.
  Топики создаёт одноразовый сервис `init-topics`:
  - `events` — 3 партиции, RF=3, `min.insync.replicas=2`
  - `events.dlt` — 3 партиции, RF=3
  Брокеры доступны и из сети compose (`kafka-N:9092`), и с хоста
  (`localhost:29092/29093/29094` — для CLI-утилит).
- **Продюсеры**: 3 пода, ключ = `user_id` (или без ключа при `KEY_MODE=none`),
  `acks=all`, `enable.idempotence=true`, ошибки доставки логируются,
  при SIGTERM буфер досылается (`flush`).
- **Консьюмеры**: группа `events-processor`, 3 пода, автокоммит выключен,
  оффсет коммитится только после успешной записи в sink. При ребалансе
  обработанные оффсеты коммитятся в `on_revoke`. Ядовитые события после
  3 попыток уходят в `events.dlt` с заголовками `error_reason`,
  `origin_event_id`, `attempts` (+ исходные topic/partition/offset в headers).
- **Sink**: Postgres, запись идемпотентна по `event_id`
  (`INSERT ... ON CONFLICT DO NOTHING`), дубли считаются счётчиком.

## Эксперименты с отказами

### №1 - Убить (kill -9) один под-консьюмер.

#### Гипотеза
Оставшиеся 2 консьюмера перехватят партиции погибшего (ребаланс); 
обработка возобновится с последнего заккоммиченного оффсета. События, которые 
обрабатывались, но не были заккоммичены, будут перечитаны и продублированы, 
однако дедупликация по event_id их отбросит. Потерь нет: seq у каждого 
пользователя непрерывен (пропусков нет, ядовитые — в DLT), нарушения порядка 
не фиксируются, т.к. события одного пользователя всегда попадают в одну 
партицию (ключ = user_id) и обрабатываются последовательно.

```bash
docker compose kill consumer-2
make verify
```
#### Результат
Seq у каждого пользователя непрерывен, нарушения порядка не фиксируются

### №2 - Остановить два брокера. 

#### Гипотеза
При остановке одного брокера — партиции с лидером на нём перейдут на оставшиеся 
ISR; с acks=all и min.insync.replicas=2 продюсеры продолжат работу, 
т.к. ISR останется >= 2. При остановке второго ISR упадёт до 1, продюсеры начнут 
получать NOT_ENOUGH_REPLICAS, консьюмеры — читать с оставшегося брокера. 
После возврата обоих брокеров синхронизация восстановится, ошибки доставки 
уйдут в ноль, verify покажет отсутствие потерь.

```bash
docker compose stop kafka-1
docker compose stop kafka-2
docker compose start kafka-1 && docker compose start kafka-2
make verify
```

#### Результат
После возврата обоих брокеров синхронизация восстановилась, verify показал 
отсутствие потерь

### №3 - KEY_MODE=none

#### Гипотеза
Без ключа партиционер распределяет сообщения по партициям последовательно 
(round-robin в рамках батча), поэтому события одного пользователя попадают 
в разные партиции и параллельные консьюмеры пишут их в sink в произвольном 
порядке относительно seq. Verify покажет нарушения порядка. 
Потерь при этом нет — репартиционирование не влияет на семантику at-least-once, 
дубликаты по-прежнему подавляются.

```bash
make verify
make key-none     # перезапуск продюсеров без ключа
# дать поработать 1–2 минуты
make verify
```

#### Результат
Присутствует нарушение порядка. Пробелы в последовательностях отсутствуют, 
потерь нет. дубликаты подавляются.
